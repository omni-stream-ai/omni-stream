---
name: omnistream-project-management
description: Distinguish immediate requests from recurring delegations, manage long-lived automations, and resolve optional project contexts.
---

Handle immediate requests in the current conversation. Research, analysis, file operations and coding are assistant capabilities, not reasons to create tasks. Delegate to a configured Agent when the tools cannot perform the work. Do not fabricate current information, successful execution or delivery.

A user task is a long-lived delegation that must continue after this conversation: scheduled execution, repeated work or periodic condition checks. “Collect AI news every day at 9” qualifies without the words “create a task”; “collect today's news” and “fix this bug” do not. Ask for missing instructions, timing or timezone rather than guessing. Projects are optional; do not demand a repository for general work.

Use `list_automations` to inspect actual delegations and run history. Use `propose_automation` with title, goal and schedule to save a pending draft; schedule is either daily (hour, minute, optional second, utc_offset_minutes) or interval (seconds, at least 60). Optional project must be an existing absolute directory. The host binds delivery to the current conversation. Explain that the user must open the recurring tasks panel and confirm activation. Do not claim the draft is enabled. Check for an existing draft before proposing a duplicate. Activation is deliberately unavailable as a model tool.

Use `pause_automation`, `resume_automation`, `cancel_automation`, or `run_automation` with id only when the user requests that operation. Resolve ambiguous targets first. Pause blocks future triggers while the current run continues; cancellation also requests interruption and is terminal. A run is one execution of a delegation, never a new user task.

Results remain in the in-app receiving conversation. Optional delivery_targets use type=plugin_action, unique id, plugin, action, fixed destination, payload and max_attempts (1–3). First inspect installed actions and their delivery_destination_fields; resolve destination IDs using read tools, never guess. Only connected, write-enabled delivery actions are allowed. Payload supports {{run.output_markdown}} and cannot change destination fields. Show account, action and destination before the user activates the draft. Core stores a revocable connection reference, not credentials. Generation does not send; Core records each target separately. Unknown results must not be retried. Do not promise unsupported applications or OS notifications.

Compose schedule with calendar={weekdays:[1,2,3,4,5],include_dates:[],exclude_dates:[]}; Monday=1 through Sunday=7, empty means daily. Overrides contain date (YYYY-MM-DD), source and reason. Exclusions win over inclusions, then weekdays. Daily dates use the fixed UTC offset; interval dates use UTC. No built-in country holiday dataset: verify sources and express holidays/make-up days as overrides. With explicitly authorized allow_calendar_updates=true, update_automation_calendar({id,calendar,reason}) may change this task's overrides, never base weekdays or shared calendars. Running Agents get automation_calendar bound to their own task/run. Do not infer permission to enable this setting.

Optional time_window is {kind:"lookback",seconds:86400} or {kind:"previous_effective_day",hour:12,minute:0,second:0}, using the same calendar. Clarify cutoff times later than execution. Data collection, message summaries and code statistics belong in goal. Condition monitoring uses interval polling, not events; silent_unmet=true requires {output_markdown,condition_met}, suppressing delivery only for definite false. delivery_policy supports independent, fail_fast and fallback_in_app.

Register or locate projects only when needed for file operations. Use `list_projects` and exact name/path matching, `register_project` for an existing supplied directory, and the established rename/delete/archive tools. Never invent a project path. Conversation management remains independent from recurring delegations.


Optional confirmation={before_seconds:600,on_timeout:"skip"} requests in-app user approval before every occurrence. Lead time is 1–604800 seconds; skip (default) expires unconfirmed runs at scheduled time, wait keeps one occurrence pending, run executes at scheduled time without a per-run approval. Manual runs also require approval and always wait. No business work or external delivery happens before scheduled time. Unless the user explicitly configured run, approval is required. With run, Core freezes the approved revision or the original goal snapshot when unconfirmed; pending edits and ongoing discussion do not delay or change the fallback. Record the execution source as timeout, never as user approval. Users may discuss and revise one occurrence in its dedicated conversation; only the user can approve or skip via the card/API. Revisions revoke older approval. Edits affect this occurrence unless the user explicitly chooses to apply the goal to future runs. In a confirmation discussion, automation_confirmation reads or updates only the bound goal with revision and reason; it cannot approve, change scheduling/delivery, or perform external writes. Do not claim a chat reply confirms execution.
